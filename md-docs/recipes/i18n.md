# 28. Internationalisation

This chapter shows you how to make your site speak several languages. You
keep its text in one JSON file per *locale* — a language, and optionally a
region, named by a tag such as `en`, `ar` or `pt-BR` — and read it with
`t("key")`. Switching the locale redraws every translated string, turns the
document right to left where the language reads that way, and changes how
`format` and `ago` write numbers and dates.

In this chapter you will:

- set up the translation files, or start a project already translated;
- translate text with `t()`, with placeholders and plural forms;
- translate a project by the words it is written in;
- switch the locale, and choose the one a page opens in;
- format numbers and dates for the reader's locale;
- check what each locale lacks.

## Set up the translation files

To translate a site, list its locales in `webfluent.app.json` under
`i18n`. `default_locale` names the language the site is written in, and
`dir` the directory that holds the files:

```json
{
  "i18n": {
    "default_locale": "en",
    "locales": ["en", "ar", "es"],
    "dir": "src/translations"
  }
}
```

Then put one file per locale in that directory — `en.json`, `ar.json`,
`es.json`. Each is a flat map of keys to messages; by convention a key has
dots in it to group related messages. This is `src/translations/en.json`:

```json
{
  "nav.home": "Home",
  "nav.about": "About",
  "welcome": "Welcome, {name}!",
  "items.one": "{count} item",
  "items.other": "{count} items",
  "actions.save": "Save"
}
```

And this is `src/translations/ar.json`, with the six plural forms Arabic
uses:

```json
{
  "nav.home": "الرئيسية",
  "nav.about": "حول",
  "welcome": "أهلاً، {name}!",
  "items.zero": "لا عناصر",
  "items.one": "عنصر واحد",
  "items.two": "عنصران",
  "items.few": "{count} عناصر",
  "items.many": "{count} عنصراً",
  "items.other": "{count} عنصر",
  "actions.save": "حفظ"
}
```

A locale with no file, and a key one locale has and another lacks, are
build warnings (`I03`). At run time a key missing from the reader's locale
falls back to the default locale's message, then to the key itself.

## Start a project translated

To begin a new project in several languages, pass `--locales` to `wf init`,
with the default locale first:

```bash
wf init my-app --locales en,ar
```

This works for the `spa` and `static` templates. The new project has:

- the `i18n` config above, and `meta.lang` set to the default locale;
- every visible string of the starter passed through `t("…")`;
- a language switch with one entry per locale;
- a file for each locale in `src/translations/`. The default locale's holds
  the starter's English, which its pages and tests are written in. Arabic
  holds the starter's Arabic. Any other locale starts as a copy of the
  English, for you to translate.

Each locale is a language tag (`en`, `ar`, `pt-BR`). `--locales ar,en`
makes Arabic the default, so the page is right to left from the first
paint. From Rust, the same is
`webfluent::init::create_with(dir, name, &Options { template, locales })`.

## Translate text with `t()`

To show a message in the reader's language, call `t("key")` wherever a
string goes. Pass a map as the second argument to fill placeholders and to
pick a plural form:

```wf
type User { name: String }

page Home(path: "/", title: "Home", description: "The home page.") {
    state user = User(name: "Sam")
    state items: [String] = ["a", "b", "c"]
    Heading(t("welcome", { name: user.name })).h1
    Text(t("items", { count: items.length }))
    Button(t("actions.save")).primary
}
```

In English this page reads **Welcome, Sam!**, **3 items** and a **Save**
button; in Arabic, **أهلاً، Sam!**, **3 عناصر** and **حفظ**.

How `t()` behaves:

- **It follows the locale.** `t("key")` is the message for the current
  locale, and every call is evaluated again when the locale changes.
- **It fills placeholders.** `t("key", { name: value })` replaces each
  `{name}` in the message with the map's value.
- **A `count` picks the plural form.** The form comes from the locale's
  CLDR plural rules, which the browser's `Intl.PluralRules` follows too:
  Arabic has `zero`, `one`, `two`, `few`, `many` and `other`; English has
  `one` and `other`; Japanese has only `other`. A count of exactly 0 uses
  `key.zero` wherever the file has one, in any language, so English can say
  "No files" rather than "0 files". Without the form it wants, `t()` falls
  back to `key.other`, then to `key`.
- **A key's forms all come from one language** — the reader's, when its
  file has the key at all, otherwise the default locale's. It never mixes
  one form from each.
- **The pre-rendered page is already translated.** The build resolves `t`
  for the default locale when it pre-renders a page, by the same rules, so
  the HTML is in the default language, its counts in that language's forms.

> [!WARNING]
> Never build a sentence from pieces (`t("greeting") + name`). Word order
> differs between languages. Put a placeholder in the message, so a
> translator can move it.

## Translate by the words as written

To translate a project that was written in one language from the start,
without inventing keys, set `"literals": true` in its `i18n` config. Every
string a reader sees is then looked up in the reader's table by its text as
written — an element's text, and props such as `label:`, `title:`,
`placeholder:`, `aria-label:` and `alt:`. The Arabic table maps the English
words to their translation:

```json
{ "Problems": "المشاكل", "{count} missing": "{count} مفقودة" }
```

The page keeps its English words:

```wf
Heading("Problems").h2          // المشاكل, for a reader in ar
Text("{l.count} missing")       // one key, `{count} missing`
```

How the text becomes a key:

- **A splice of a plain path is a placeholder.** It is named for the
  path's last part, so `"{l.count} missing"` is the key `{count} missing`.
  A splice of anything more, such as `"{n + 1} more"`, keeps the text as
  written.
- **Each branch of an `if` is its own key** when the text chooses between
  them.
- **A value shown by its name** — a `derived` or `state` — is looked up
  only when its name says it is words, such as `countText` or
  `emptyLabel`. Shown words that neither rule covers draw an `I05` warning.
- **What is not words is left alone:** an icon's name, `Code(…)`, and a
  component named `Kbd`.
- **A list of words is translated word by word.** A `labels:` prop, which
  holds one word for each option of a control whose options are values,
  is looked up item by item: `Segmented(options: ["2", "4"], labels: ["2
  spaces", "4 spaces"])` on your own `Segmented` component.

The default locale's messages are the words themselves, so its file may be
empty. `wf translations` counts each string as a key in use, and lists what
another locale has not translated as missing.

### Count by the number in the text

A literal with one number spliced into it picks its plural form by that
number. The key's plural forms are keys too, as for `count`:

```json
{
  "{files} files.zero": "لا توجد ملفات",
  "{files} files.one": "ملف واحد",
  "{files} files.two": "ملفان",
  "{files} files.few": "{files} ملفات",
  "{files} files.many": "{files} ملفًا",
  "{files} files.other": "{files} ملف"
}
```

```wf
Text("{files} files")           // 11 ملفًا, for a reader in ar
```

The default locale gives its forms the same way — `"{files} files.one":
"{files} file"` — where its words differ by count. With two numbers in the
text, neither is taken as the count: the message is looked up as written.

## Switch the locale

To let the reader change language, call `setLocale(code)`. This app puts a
language picker in the navigation bar:

```wf
app {
    state chosen = "en"
    Navbar {
        Navbar.Brand { Link("i18n", to: "/") }
        Navbar.Links {
            Link(t("nav.home"), to: "/")
            Link(t("nav.about"), to: "/about")
        }
        Navbar.Actions {
            Select(bind: chosen, label: t("nav.language")) {
                on change { setLocale(chosen) }
                Select.Option("English", value: "en")
                Select.Option("العربية", value: "ar")
                Select.Option("Español", value: "es")
            }
        }
    }
    Router
}

page Home(path: "/", title: "Home", description: "The home page.") {
    Heading("Home").h1
    Text("Locale: {locale}, direction: {dir}")
    if locale == "ar" { Text("النسخة العربية") }
}
```

`locale` is the current locale's code, and `dir` is `"ltr"` or `"rtl"`.
An `app` block may declare `state` as a page does, as `chosen` is here.

On a switch, the runtime sets `<html lang>` and `<html dir>`. A locale is
right to left when its language is: Arabic, Hebrew, Persian, Urdu, Pashto,
Sindhi, Central Kurdish, Uyghur, Yiddish, Dhivehi, Kashmiri, Syriac,
Aramaic and N'Ko — with any region, so `ar-EG` is too. A site whose default
locale is one of them is written `<html lang="ar" dir="rtl">` from the
start, before any script runs.

`meta.lang` may name a region of the default locale's language (`en-GB` for
`en`); otherwise the default locale is the page's language.

The built-ins use logical CSS properties (`margin-inline-start`, not
`margin-left`), so their layouts mirror with no work on your side. Use
logical properties in your own `style { }` blocks too.

## Choose the locale a page opens in

A page opens in `default_locale`, with two exceptions:

1. **The address names a locale.** `?lang=<code>`, for one of the
   configured locales, opens the page in it: `/about?lang=ar` is the Arabic
   page, for a link you share. It does not change the reader's kept
   choice. It is not an address a search engine indexes: its HTML, and its
   canonical link, are the default locale's, so the build lists no `?lang=`
   address as an `hreflang` alternate. To have each language found, give
   it pages of its own ([A page in its own language](#a-page-in-its-own-language)).
2. **The reader chose a locale before.** `setLocale(code)` keeps the code
   in the reader's `localStorage`, under `wf:locale`, and every page loaded
   after that opens in it, on this visit and the next. Choosing
   `default_locale` again forgets it.

So a static site, which loads each page afresh, keeps the reader's language
from page to page, and a language switch can be a pair of buttons:

```wf
app {
    Navbar {
        Navbar.Brand { Link("i18n", to: "/") }
        Navbar.Actions {
            Button("English") { on click { setLocale("en") } }
            Button("العربية") { on click { setLocale("ar") } }
        }
    }
    Router
}
```

The runtime does not guess from the browser's language. Nothing is kept
until the reader chooses, so a first visit gets the `?lang=` locale or the
default, and a search engine's crawler the default. To start a first visit in the
browser's language, keep whether the reader has chosen in a store with
`persist`, and until they have, call
`setLocale(navigator.language.slice(0, 2))` from an `effect` in the app.

A static build pre-renders every page once, in the default locale; another
locale is applied as the page loads. So a search engine indexes only the
default locale's text. For each language to be found, give it pages of
its own ([A page in its own language](#a-page-in-its-own-language)).

## A page in its own language

`t()` and `setLocale` translate a page in the browser, at one address. A
search engine indexes what that address's HTML says, which is the default
locale. A site that wants each language found writes each page once per
language, at an address of its own, and says so:

```wf
page Home(path: "/", title: "منذر عمر", description: "مهندس خلفيات.") {
    Heading("مرحباً").h1
}

page HomeEn(path: "/en", title: "Monzer Omer", description: "Engineer.",
            lang: "en", translates: Home) {
    Heading("Hello").h1
}
```

- **`lang:`** is the language the page is written in. A page without one
  is in the site's (`meta.lang`, or `default_locale`). The page is written
  `<html lang="en">`, with `dir="rtl"` for a language written right to
  left, and its `og:locale` and its JSON-LD's `inLanguage` say the same.
  The router sets `lang` and `dir` on `<html>` when it shows the page, and
  puts back the site's (or the locale the reader chose) on a page without
  one.
- **`translates:`** names the page this one is a translation of. Pages
  joined this way — `HomeFr` may translate `Home` too — each list all of
  them as `hreflang` alternates, at their own addresses and canonical to
  themselves, with `x-default` for the one in the site's language, and
  each names the others' languages as `og:locale:alternate`.
- A `:param` page's translation is matched by its parameters:
  `/en/posts/:slug` for `/posts/:slug`, filled with the same `slug`.

A `translates:` that names no page, or two translations of one page in one
language, is `R05`.

## Format numbers and dates for the locale

`format` and `ago` follow the current locale
([Expressions](../reference/expressions.md)). `format(1234.5, .currency, "EUR")` is
`€1,234.50` in `en` and `1.234,50 €` in `de`; `ago(date)` says
"il y a 3 jours" in `fr`. The pre-rendered page uses a table of the common
locales' separators and currency symbols, and the live page uses the
browser's `Intl` and corrects any difference.

To choose the digits a locale writes, add the Unicode extension to its
code:

- `setLocale("ar-u-nu-arab")` reads the `ar` table and writes `format` —
  a date pattern too, its AM/PM in the locale's words — `ago` and every
  count in Arabic-Indic digits (١١ ملفًا).
- `setLocale("ar-u-nu-latn")` writes them in 0–9, whatever the browser's
  Arabic would pick.
- Bare `ar` leaves the digits to the browser.

A count is prose, so it takes the locale's digits. Another number spliced
into a message — a line number, a version — stays as it is. The document's
`lang` is the language, `ar`, whatever digits the code names.

## Translate long-form text

For a paragraph or a page of prose:

- Under `"literals": true`, `Markdown("…")` written in place is words like
  any other text: its whole source, `**` and all, is the key.
- Text inside a `.md` page is not passed through `t`. Keep one Markdown
  file per locale, each with its own `path`, `lang` and `translates` in
  its front matter, or keep the text in the translation file under a key
  and render `Markdown(t("about.body"))`.

## Check what each locale lacks

To see the translations as a table, run `wf translations`:

```bash
wf translations
wf translations --missing ar
wf translations --unused
wf translations --plurals
```

| Command | What it prints |
|---|---|
| `wf translations` | Each locale, the plural forms its rules use, and how many keys it lacks, a form it lacks, or a placeholder that differs from the default locale's |
| `--missing ar` | What Arabic lacks |
| `--unused` | The keys nothing names |
| `--plurals` | CLDR's plural rules: every locale's forms |
| `--json` | The whole table: each key with its message in every locale, and every place a `t()` names it |

From Rust the table is `webfluent::i18n::table` (with the `internals` feature, outside semver), which can also write one
message back into its file with every other byte as it was.

## Checklist

- Every visible string goes through `t`, including `label:`,
  `placeholder:` and `aria-label:` values.
- No sentence is built from parts (`t("x") + name`); a placeholder lets a
  translator reorder it.
- Every count has its plural forms, even in English, and a `zero` where
  "none" reads better as a sentence.
- `wf translations --missing <locale>` lists nothing for any locale.
- You have tried the site once in a right-to-left locale, and checked:
  - alignment, and icons that imply a direction (arrows);
  - any `left` or `right` in your own CSS;
  - a Latin code or figure inside Arabic text, which needs a left-to-right
    run of its own (`direction: ltr; unicode-bidi: isolate`) to keep its
    parts in order.
- If each language should be found by search, each has pages of its own,
  with `lang:` and `translates:`, and `wf check` reports no `R05`.
