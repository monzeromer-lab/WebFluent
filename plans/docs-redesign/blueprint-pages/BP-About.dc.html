How reactivity works

WebFluent has no render function and no virtual DOM. The compiler works out, from the source, which piece of the page reads which value, and ties them together. This essay argues that is the right default, says what it costs, and says when you will notice.

9 minutesUpdated for 6.0Monzer Omer

The question every framework answers

A value changes. What on the screen has to change with it? There are two ways to find out. One is to draw everything again and compare the result with what is there; that is what React does, and it is why a React component is a function that runs again. The other is to know in advance who reads what, and to tell only those readers.

WebFluent takes the second way, and takes it at build time. A page is not a function that runs again; it runs once, and what it leaves behind is a set of small subscriptions.

What the compiler knows

Here is a page with one value you change and one value worked out from it:

page Cart(path: "/cart", title: "Cart") {
    state count = 3
    derived double = count * 2

    Text("{double} items")
    Button("Add").primary { on click { count = count + 1 } }
}

The compiler reads Text("{double} items"), sees that it reads double, and sees that double reads count. Those are the only edges in the graph:

Solid and Svelte 5 make the same bet with signals. The difference here is that the graph is known before the page ships, so the compiler can check it: an effect that writes what it reads, every run, is X02, refused at build time rather than found by a frozen tab.

What it costs

A value is followed only where WebFluent can see it being read. A plain script under src/ that reads count once gets a number, not a subscription. When a script needs to follow a value, hand it the value through update:, which runs again whenever what it reads changes, or hand it an action to call.

The other cost is that a state is read once, when it is made. That is what you want almost always, and the one time it is not, the compiler says so.

When you will notice

Two places, both with a finding of their own. A state made from now holds the moment the page opened and never ticks; the fix is derived, and X06 offers it. A for with no by whose items hold state starts those items again when the list changes; give it a key, and U09 says which.

Everywhere else, the right thing redraws and nothing else does, and you do not have to think about it. That is the point.
