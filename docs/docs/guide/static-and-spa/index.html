Static or single-page

The same source builds as pre-rendered pages or as one app shell. What each gives you, what the pre-rendered page holds, and how dynamic routes are rendered.

The same WebFluent source builds a site in one of two shapes: a static site, with a pre-rendered HTML file for every route, or a single-page app, with one shell that draws every page in the browser. One setting, build.ssg, picks the shape, and you can change it at any time. This chapter explains what each shape gives you and how a static page comes to life, then shows you how to pre-render dynamic routes, add a 404 page and host either shape.

In this chapter:

  • what the two shapes write, and when to choose each;
  • how hydration takes over a pre-rendered page;
  • what the build can and cannot know when it pre-renders;
  • how to switch shapes, pre-render dynamic routes, add a 404 page, serve a single-page build and serve the site under a sub-path.

When to choose each

Choose static for anything people find by searching or share by link: marketing sites, docs, blogs, shops. The text is in the HTML, so search engines and link previews see the real page.

Choose single-page for an app behind a sign-in, where every page is personal and moving between pages fast matters more than the first paint. Choose it too when your host cannot serve a file per route.

Hydration

A static page is readable before any script runs. When app.js arrives, it hydrates the page: it draws the page beside the one already there, then takes the painted one over in place.

What happens to each part of the page:

  • An element nothing holds on to stays exactly as it was painted. Its attributes are brought up to date; it is never moved or drawn again.
  • An element that a handler, an effect, a ref or a widget holds is put where the painted one stood, inside the painted parent.
  • Text that a signal keeps current changes inside the painted element.

The reader never sees the page flash or redraw, and keeps their scroll position, their focus and anything they had selected. The page's largest paint stays the first one, which is what a search engine's speed score measures.

Under wf serve, the runtime compares the page it took over with the one it drew, and says so in the console when they differ. A difference is a WebFluent bug, never yours.

For the first paint to be right, prefer what the build can see:

  • Data files over fetches for content that changes only when you deploy (Fetching data).
  • Responsive values over viewport for layout.

Switch between static and single-page

To build a static site, set ssg in the config:

json

{ "build": { "ssg": true } }

"output_type": "static" means the same as "ssg": true. Set ssg to false, or leave it out, for a single-page build.

wf init -t static starts a project with ssg on; wf init -t spa starts one with it off. You can change your mind at any time — the source does not change.

Pre-render a dynamic route with paths:

A page on a :param route, such as /posts/:slug, has no single file to write. To pre-render it, list the values in paths:, and the build writes one HTML file for each.

This blog writes one file per post in posts.json:

wf

type Post { slug: String, title: String, date: String, body: String } data posts: [Post] = "posts.json" page PostPage(path: "/posts/:slug", slug: String, title: "Post", description: "A post.", paths: posts.map(p => p.slug)) { derived post = posts.find(p => p.slug == slug) head { meta(property: "og:title", content: post?.title ?? "Post") } if let p = post { Heading(p.title).h1 Markdown(p.body) } else { Alert("No such post").warning } }

For a post whose slug is hello, the build writes posts/hello/index.html, with that post painted and listed in the sitemap.

The rules for paths::

  • It must be known at build time: a data file, a const or a literal list.
  • For a route with several parameters, each value is a map that names them: paths: pairs.map(x => { year: x.y, slug: x.s }).
  • Each value is seeded as the parameter (and as params.slug), painted, and listed in the sitemap.
  • A value that is not in paths: has no file, so a static host answers with 404.html.
  • A single-page build does not need paths: at all.

Give each file its own title

title: and description: may name the page's parameters — title: "{slug} — Blog" — and each file gets its own. A title may also look the entry up: title: "{posts.find(p => p.slug == slug)?.title ?? slug} — Blog". Tags beyond the title and description go in head { } (Content).

Add a 404 page

To show a page for a route no other page claims, declare a page on the * route:

wf

page NotFound(path: "*", title: "Not found", description: "There is no page at this address.") { Heading("Page not found").h1 Link("Go to the home page", to: "/") }

The router shows it for any address no page claims. In a static build it is also written as 404.html, which GitHub Pages, Netlify, Cloudflare Pages and most static hosts serve for a path they have no file for.

Serve a single-page build

A single-page build has one file, index.html, so every path a reader might open — /users/42 — has to reach it. Most hosts need one line for this; Deploying has each in full:

text

Netlify / Cloudflare Pages public/_redirects: /* /index.html 200 nginx try_files $uri $uri/ /index.html; Vercel "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]

Warning

Without this rule, the home page works, but a reload on any other address is a 404.

Serve the site under a sub-path

To serve the site under a path such as /my-site — a GitHub Pages project site — set build.base_path:

json

{ "build": { "ssg": true, "base_path": "/my-site" } }

The build prefixes every link, every asset and the router's paths with it. Write your paths from the site's root as if there were no prefix: Link("About", to: "/about") links to /my-site/about.
