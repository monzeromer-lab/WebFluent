Accessibility

Build pages that work with a keyboard, a screen reader or voice control: what the built-ins do, what the compiler checks, and what is still yours to do.

This chapter shows you how to build pages that people can use with a keyboard, a screen reader, voice control, zoom or reduced motion. Most of the work is done for you: the built-ins render the markup assistive technology expects, the router and forms manage focus, and the compiler checks every page on every build. What is left — meaning, wording, order — is yours, and this chapter lists it.

In this chapter you will:

  • learn what the built-ins already do, so you do not redo it;
  • fix what the compiler reports;
  • do the work no compiler can check;
  • label controls well;
  • test a page the way its readers use it.

Know what the built-ins do for you

You get these behaviours without asking, as long as you use the built-in elements rather than rebuilding them:

  • Semantic elements. A Button is a <button>, a Link an <a>, Heading(…).h2 an <h2>. Header, Section and Footer are landmarks. A Table is a <table> whose head cells are <th scope="col">, a List is a <ul> or <ol>, and the page's content is a <main>.
  • A skip link. It is first in the tab order, visible when focused, and jumps past the navigation to the content.
  • Route changes that behave like page loads. Focus moves to the new page's heading, the scroll returns to the top, and the new title is announced.
  • Labelled fields. label: is a real <label for>. hint: and the error are tied to the control with aria-describedby. An error sets aria-invalid and is announced when it appears (Forms).
  • Forms that point at the problem. A submit that fails moves focus to the first field with an error and announces it.
  • Dialogs that hold focus. Modal and Dialog are real <dialog> elements: the rest of the page is inert, Escape closes them, and focus returns to what opened them.
  • Focus held where you ask. Any other element holds focus with trapFocus: open — a find bar, a panel. Focus moves in, Tab and Shift+Tab go round inside it, a click outside brings focus back, and when open turns false, focus returns to where it was.
  • Menus with the keys people expect. The arrow keys move and skip a disabled item, Home and End jump to the ends, Enter and Space choose, ArrowRight opens a submenu and ArrowLeft leaves it, and Escape closes the innermost menu and returns focus. A check item is a menuitemcheckbox with aria-checked; an item's shortcut is its aria-keyshortcuts.
  • Splitters you can move without a mouse. A Splitter is a separator with its size as aria-valuenow. It takes focus, the arrow keys move it, Home and End go to its ends, and Enter resets it.
  • Announcements. A Toast is spoken politely. To announce anything else, call WF.announce(text).
  • The active link. The link to the current page carries aria-current="page".
  • Reduced motion. A reader who asked for it gets no animation at all, and a carousel does not play on its own (Motion).
  • Visible focus. Every interactive built-in shows a focus ring for the keyboard (:focus-visible), but not on every click.

Fix what the compiler reports

The compiler checks every page for the mistakes it can see in the markup, and reports each as a warning on every build and in the editor. Each code has a full entry, with a fix, in Diagnostics, and wf explain CODE prints it in your terminal.

Fix what the compiler reports
Code What it checks

A01

Every Image has alt: (an empty one for a decorative picture)

A02

Every IconButton has a label:

A03, A04

Every Input, Checkbox, Radio, Switch, Slider and Textarea has a label

A05, A06, A07

 Buttons, links and headings have text

A08

Every Modal and Dialog has a title:

A09

 A video has captions and controls; audio has a transcript

A10

 A table has a header row

A11, A12

No heading level is skipped, and each page has exactly one h1

A13

 The theme's text and background colours meet WCAG AA contrast

A14

A role: holds children of the roles it requires

A15

A control's aria-label contains its visible text, for voice control

A16

No literal id: is shared by several elements, in a loop or a reused component

A17

Every Frame has a title:

For example, this button's aria-label does not contain the word it shows, so a voice-control user who says "click Save" may not reach it:

wf · draws A15

page Editor(path: "/", title: "Editor", description: "Write a note.") { Heading("Editor").h1 Button("Save", aria-label: "Submit the form") }

The fix is to start the aria-label with the visible words: aria-label: "Save the note".

Do what the compiler cannot check

The compiler can see markup; it cannot see meaning. These are still yours:

  • Alt text that says what the picture shows, in its context. "Photo" passes A01 and helps nobody.
  • Link text that says where it goes. Twelve "Read more" links pass A06.
  • An order that makes sense. The reading order is the source order. Do not rearrange it visually with order: or absolute positioning.
  • Colour that is not the only signal. An error in red also says so in words; a chart has labels.
  • The contrast of your own styles. A13 checks the theme's tokens, not a colour written directly in a style { } block.
  • Custom controls. A Card made clickable with on click is not a button to a keyboard (Make a custom control work from the keyboard).
  • Time limits. A Toast disappears. Anything the reader must act on belongs in an Alert that stays.

Make a custom control work from the keyboard

Use Button whenever you can. When an element must act as a button, give it the role, a place in the tab order, and handlers for the keys a button answers to:

wf

page Plans(path: "/plans", title: "Plans", description: "Choose a plan.") { state chosen = "" Heading("Plans").h1 Card(role: "button", tabindex: "0") { on click { chosen = "Team" } on key("Enter") { chosen = "Team" } on key("space") { chosen = "Team" } Text("Team plan") } Text("Chosen: {chosen}") }

Without tabindex, the card cannot be reached with Tab; without the key handlers, reaching it does nothing.

Label controls well

Every control needs a name that assistive technology can read, and that matches what a sighted reader sees:

wf

page Search(path: "/", title: "Search", description: "Find a page.") { state q = "" Heading("Search").h1 Input(bind: q, label: "Search the docs", hint: "Try “routing” or “forms”").search IconButton(icon: "close", label: "Clear the search") { on click { q = "" } } Button("Search", aria-label: "Search the docs") { on click { log(q) } } }
  • Prefer a visible label: to a placeholder. A placeholder disappears as soon as the reader types.
  • Name an icon-only control. Use label: on an IconButton, or aria-label: on anything else. The name is read aloud, never shown.
  • Begin an aria-label with the visible words. Someone who says "click Search" then reaches the right button (A15).

Test with assistive technology

The compiler's checks are a floor. Before you ship a page, use it the way its readers do:

  1. Use only the keyboard. Put the mouse away. Tab through the page, open and close every menu and dialog, and submit every form. Focus is always visible and never lost.
  2. Use a screen reader. VoiceOver (macOS: ⌘F5), NVDA (Windows, free) or TalkBack (Android). Listen to the page's list of headings and landmarks, and to what a form says when it fails.
  3. Zoom to 200%, and narrow the window. Nothing needs horizontal scrolling.
  4. Turn on reduced motion in your system settings, and reload. Nothing moves.

You can also automate part of this. wf test's click "Save" and type "…" into "Email" find controls by the name a reader sees, the way assistive technology does, so a test that passes is a page someone can operate (Testing).

Checklist

  • wf check reports no A warnings.
  • Every picture's alt text says what it shows, and decorative ones have alt: "".
  • Every link and button says what it does without the text around it.
  • Every control has a visible label, and every aria-label contains the visible words.
  • Colour is never the only way something is said.
  • Every custom control is reachable with Tab and works with Enter and Space.
  • The page works with only a keyboard, with a screen reader, at 200% zoom, and with reduced motion.
