Chapter 36

Tutorials

Three projects built step by step — a todo app, a statically built notes site, a budget tracker — none needing a server.

These three tutorials each build a whole project, step by step, and each project is complete in the repository under examples/tutorials/. None needs a server: what a project keeps, it keeps in the reader's browser. Each tutorial stands on its own, so pick the one that matches where you are, or do them in order.

If you have not written WebFluent before, start with the Shelf tutorial: it is a gentler first half hour.

Before you start

You need:

  • wf installed and on your PATH — wf --version prints wf 5.11.0 or later (Getting started).
  • Chrome or Chromium on the machine, for the tests that click and for wf verify. Set WF_CHROME to its path when it is not in a usual place.
  • Git, to fetch the finished projects.

Every code block whose first line names a file — // src/stores/Todos.wf — is that file, or a run of lines from it, exactly as the project has it. A test holds this chapter to the projects, so the code you read here is the code that builds.

To start from a finished project instead, clone the repository and serve one:

bash

$ git clone https://github.com/monzeromer-lab/WebFluent $ cd WebFluent/examples/tutorials/easy-todos $ wf serve

Check it: the terminal prints Starting dev server at http://localhost:3000/, and that address shows the project.

Easy: Todos

What you will build. A list of things to do, kept in the reader's browser: add a todo, tick it, rename it, remove it, and show only the open ones. It is one page, one store and one component. The finished project is examples/tutorials/easy-todos.

Time: about 20 minutes.

Before you start. You need only wf and Chrome. You write every file of this project yourself, and the blocks below hold each file whole, except the tests, where one of six is shown.

Step 1: Create the project

Make a single-page project and go into it:

bash

$ wf init todos -t spa $ cd todos

Delete everything the template put in src/ and in tests/: you write every file yourself, and the template's tests would fail without its pages. Then replace webfluent.app.json with this:

json

{ "name": "todos", "version": "1.0.0", "theme": { "name": "Paper", "dark": "Night" }, "build": { "output": "./build", "output_type": "spa", "csp": true }, "meta": { "title": "Todos", "description": "A small list of things to do, kept in your browser.", "lang": "en", "favicon": "/favicon.svg" } }
  • "output_type": "spa" makes a single-page app: one HTML shell, with pages swapped without a reload (Static sites and SPAs).
  • "csp": true ships a content security policy and holds the build to it (Security).
  • theme names two themes, Paper and Night, which you write in the next step.

Check it: wf check prints IO Error: No .wf files found in src/. That is expected: src/ is empty until the next step.

Step 2: Give it a look of its own

The config names a theme, so declare it first. A theme names only the design tokens it changes; every other token keeps its default (Styling). Night is the theme named as "dark" in the config, and the page uses it when the reader's system is set to dark:

wf

// src/theme.wf /// Warm paper and ink, with one teal for what you can act on. theme Paper { color-primary: #0F766E color-background: #F6F4EF color-surface: #FFFFFF color-text: #1F2328 color-text-muted: #5E6670 color-border: #E4E0D8 font-family: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif radius-md: 10px } /// The same page after dark. theme Night { color-primary: #2DD4BF color-background: #14171A color-surface: #1C2024 color-text: #ECEEF0 color-text-muted: #A3ABB3 color-border: #2C3238 }

The page you write in step 6 names classes — card, todo, is-done, filters — and src/todos.css styles them. The build bundles every .css file under src/, so the file needs no link. These are four of its rules; copy the whole file from the finished project:

css

.todo { flex-wrap: nowrap; padding: 0.6rem 0.25rem; border-top: 1px solid var(--color-border); } .todo__title { flex: 1; } .todo.is-done .todo__title { text-decoration: line-through; color: var(--color-text-muted); } .filters a.is-on { background: var(--color-background); color: var(--color-text); font-weight: 600; }

Each colour is a token, var(--color-border), so the dark theme recolours the page with no rule of its own.

Check it: wf check prints No problems in todos.

Step 3: Describe a todo

A type names the fields a value has, and the checker holds every use to them (Types). An enum is a fixed set of cases:

wf

// src/types.wf /// One thing to do. type Todo { id: Uuid title: String done: Bool = false } /// Which todos the list shows. enum Filter { all, open, done }
  • Uuid is one of the types the language brings; uuid() makes one.
  • done has a default, so a new todo can leave it out.
  • A case is written with a dot, .open, wherever a Filter is wanted.

Because the checker knows the fields, todo.titel is an error where it is written, and the message names the field you meant.

Check it: wf check prints No problems in todos.

Step 4: Write a store that remembers

A store holds state that any page or component can read (Stores). This one keeps the list:

wf

// src/stores/Todos.wf /// The list, kept in the browser between visits. store Todos { persist items: [Todo] = [] derived open = items.filter(todo => !todo.done) derived done = items.filter(todo => todo.done) action add(title: String) { let text = title.trim() if text == "" { return } items = items.concat([Todo(id: uuid(), title: text)]) } action toggle(id: Uuid) { items = items.map(todo => if todo.id == id { { ...todo, done: !todo.done } } else { todo }) } action rename(id: Uuid, title: String) { let text = title.trim() if text == "" { return } items = items.map(todo => if todo.id == id { { ...todo, title: text } } else { todo }) } action remove(id: Uuid) { items = items.filter(todo => todo.id != id) } action clearDone() { items = items.filter(todo => !todo.done) } }
  • persist is a state kept in the browser's storage. The list is still there after a reload, and a second tab follows the first, with no storage code written.
  • A derived value follows what it reads: open is always the todos not yet done.
  • An action is the one place state changes. { ...todo, done: !todo.done } is the todo with one field changed.
  • rename, remove and clearDone change the list in the same way.

Check it: wf check prints seven U04 warnings, such as `warning[U04]: Todos.open is declared but never read`. That is expected: nothing reads the store yet. The page in step 6 reads every member, and the warnings go.

Step 5: Build one row

A component is an element of your own (Components). This one draws a single todo, and lets the reader rename it in place:

wf

// src/components/TodoRow.wf /// One row of the list: a box to tick, the title, and buttons to rename and /// remove it. component TodoRow(_ todo: Todo) { use Todos state editing = false state draft = todo.title action save() { Todos.rename(todo.id, draft) editing = false } Row(class: ["todo", if todo.done { "is-done" }], align: .center, gap: .sm) { Checkbox(checked: todo.done, aria-label: "Done: {todo.title}") { on change { Todos.toggle(todo.id) } } if editing { // `mount:` runs when the input is made: the cursor goes straight in. Input(bind: draft, aria-label: "New title for {todo.title}", class: "todo__edit", mount: (n) => n.focus()) { on key("Enter") { save() } on key("Escape") { draft = todo.title editing = false } on blur { save() } } } else { Text(todo.title, class: "todo__title") IconButton(icon: "edit", label: "Rename {todo.title}", class: "todo__action").sm { on click { draft = todo.title editing = true } } } IconButton(icon: "trash", label: "Remove {todo.title}", class: "todo__action").sm { on click { Todos.remove(todo.id) } } } }
  • _ todo is the component's one positional prop, so a call reads TodoRow(todo).
  • Its state belongs to each row: renaming one row does not put the others in edit mode.
  • class: adds classes to the element's own. The list form may hold an if, which adds is-done only while the todo is done.
  • Every control has an accessible name. The checkbox and the icon buttons say which todo they act on, so a screen reader — and the tests in step 7 — can tell them apart (Accessibility).

Check it: wf check prints U03 for TodoRow (nothing places it yet) and four U04 warnings. The store's toggle, rename and remove no longer appear: the row calls them.

Step 6: Write the page

The page holds the box for a new todo, the filters and the list. Here is its first half:

wf

// src/pages/Home.wf page Home(path: "/", title: "Todos", description: "A small list of things to do, kept in your browser.") { use Todos state draft = "" // The filter lives in the address — `/?show=open` — so a reload or a // shared link keeps it. derived filter: Filter = if query.show == "open" { .open } else if query.show == "done" { .done } else { .all } derived shown = match filter { .open { Todos.open } .done { Todos.done } .all { Todos.items } } action add() { Todos.add(draft) draft = "" } Stack(class: "card", gap: .md) { Row(justify: .between, align: .baseline) { Heading("Todos").h1 Text("{Todos.open.length} left", class: "count") } Row(class: "new", gap: .sm) { Input(bind: draft, placeholder: "What needs doing?", aria-label: "New todo") { on key("Enter") { add() } } Button("Add", disabled: draft.trim() == "").primary { on click { add() } } }
  • bind: draft ties the input to the state both ways: typing changes draft, and draft = "" empties the box.
  • query is the address's query string as a value, kept current. So filter follows the address, and shown follows filter.
  • A match over an enum must cover every case. If you add a fourth case to Filter, this match is an error until it handles it.

The second half draws the filters and the list, and closes the page. Add it below the first, after a blank line:

wf

// src/pages/Home.wf Row(class: "filters", gap: .xs, align: .center) { Link("All", to: "/?show=all", class: { "is-on": filter == .all }) Link("Open", to: "/?show=open", class: { "is-on": filter == .open }) Link("Done", to: "/?show=done", class: { "is-on": filter == .done }) Spacer if Todos.done.length > 0 { Button("Clear done").sm { on click { Todos.clearDone() } } } } if shown.length == 0 { Text(if Todos.items.length == 0 { "Nothing yet — add your first todo above." } else { "Nothing here." }, class: "empty") } Stack(class: "list") { for todo in shown by todo.id { TodoRow(todo, animate: .fadeIn, exit: .fadeOut) } } } Text("Your list stays in this browser, and nowhere else.", class: "hint") }
  • for … by todo.id is a keyed list. When a todo is renamed, or the filter hides it, only its row changes; the other rows keep their elements, and the row being edited keeps its cursor (Control flow).
  • animate: and exit: fade a row in and out.
  • A class map, { "is-on": filter == .all }, turns a class on while its condition holds.

Last, the app declaration is the frame every page sits in. Router marks where the current page is drawn:

wf

// src/App.wf // The frame every page sits in: a narrow column, centred. app { Container(class: "shell") { Router } }

Now start the development server in a second terminal, and leave it running. Every save rebuilds the project and reloads the page:

bash

$ wf serve

Check it: wf check prints No problems in todos., and <http://localhost:3000/> shows a card headed Todos with 0 left and Nothing yet — add your first todo above. Type a todo and press Enter: it appears, and the count reads 1 left. Reload the page, and the todo is still there. Click Open, and the address becomes /?show=open.

If the server prints No theme Paper is declared in this project, you probably skipped src/theme.wf in step 2. If a store member shows as U04 here, you probably left out part of the page.

Step 7: Write tests

A test draws what it declares, then follows its steps in order. It types into the control named New todo and clicks the button named Add, the way a reader would (Testing). Create tests/todos.wf with this test:

wf

// tests/todos.wf test "adding a todo puts it in the list" { use Todos state draft = "" Input(bind: draft, aria-label: "New todo") Button("Add") { on click { Todos.add(draft) draft = "" } } for todo in Todos.items by todo.id { TodoRow(todo) } Text("{Todos.open.length} left") expect "0 left" type "Buy bread" into "New todo" click "Add" expect "Buy bread" expect "1 left" }

A test that clicks or types runs in a headless Chrome. The finished project has six tests in tests/todos.wf: two that only look at a row, and four that click — adding a todo, refusing a blank one, ticking and clearing, and renaming that keeps one row for each. Copy the file to have them all, then run them:

bash

$ wf test

Check it: with the whole file, wf test ends with 6 passed, 0 failed, 2 snapshot(s) written. The two tests that only look write a snapshot of what they drew under tests/__snapshots__/, and later runs compare against it.

If a test that clicks reports that no browser was found, Chrome is not where wf looks: set WF_CHROME to its path.

Step 8: Build it

Check, test and build the project:

bash

$ wf check $ wf test $ wf build

wf check reports every finding and writes nothing. wf build writes build/, which any static host serves — Deploying covers GitHub Pages, Netlify and the rest. To load the built page in a real browser before you deploy, run wf verify: it fails on an error, a missing file or a page that draws nothing.

Check it: wf build ends with Build complete., and build/ holds index.html, app.js and styles.css.

What you built in Todos

  • A type and an enum, held to every use (Types).
  • A store whose list survives a reload with persist, and derived values that follow it (Stores).
  • A component with state of its own, and accessible names on every control (Components).
  • A keyed list, and a filter kept in the address with query (Control flow).
  • A theme with a dark variant, and the project's own stylesheet (Styling).
  • Tests that look and tests that click (Testing).

Medium: Field Notes

What you will build. A notebook kept in public — notes from a garden, a kitchen and a few trips — built as a static site. The notes are a JSON file the build reads. Every page, including one page per note, is written out as HTML that a search engine can read. The one thing a reader changes, the notes they save for later, stays in their browser. The finished project is examples/tutorials/medium-field-notes.

Time: about an hour.

Before you start. You need wf, Chrome and a copy of the repository (see Before you start above). This tutorial shows the part of each file that teaches something new, so work in the finished project and read each file as its step comes up:

bash

$ cd WebFluent/examples/tutorials/medium-field-notes $ wf serve

The Todos tutorial explains state, stores and components; this one assumes them.

Step 1: Create a static project and its look

A new project of this kind starts from the static template:

bash

$ wf init field-notes -t static $ cd field-notes

The project's webfluent.app.json:

json

{ "name": "field-notes", "version": "1.0.0", "author": "Field Notes", "theme": { "name": "Meadow", "dark": "Dusk" }, "build": { "output": "./build", "ssg": true, "csp": true }, "meta": { "title": "Field Notes", "description": "Notes from a small garden, a busy kitchen and the roads between them.", "lang": "en", "site_url": "https://field-notes.example.com", "site_name": "Field Notes", "favicon": "/favicon.svg", "image": "/card.png", "sitemap": true } }
  • "ssg": true pre-renders every page to its own index.html. When the page loads, the script takes it over in place — hydration (Static sites and SPAs).
  • site_url lets the build write what search engines and link previews read: a canonical address, Open Graph tags, JSON-LD, sitemap.xml and robots.txt (Content).

The dark theme names only the tokens that change:

wf

// src/theme.wf /// The dark theme: only the tokens that change. theme Dusk { color-primary: #86C9A6 color-secondary: #E8A086 color-background: #121614 color-surface: #1A201D color-text: #E9E5DA color-text-muted: #A6AFA9 color-border: #2B3430 paper-raised: #171C19 tag-bg: #213129 tag-text: #A9DCC1 }

The light theme, Meadow, sets the same names. A theme may declare tokens of its own, such as paper-raised and tag-bg. The project's stylesheet, src/styles.css, reads every colour as a token (var(--tag-bg)), so the dark theme needs no rule of its own (Design tokens).

Check it: with wf serve running, set your system to dark mode. The page turns dark green and cream without a reload.

Step 2: Type the data

The notes are data, and a type says what each one holds:

wf

// src/types.wf /// One note in the notebook. type Note { slug: String title: String date: Date tags: [String] summary: String minutes: Number body: String } /// Every note, read from `notes.json` when the site is built. data notes: [Note] = "notes.json"
  • data reads a JSON file at build time. The result is a constant, typed by the annotation, inlined into the bundle and seeded into every pre-rendered page (Data).
  • The checker holds the program to Note: a page that reads note.titel is an error where it is written.
  • date is a Date: a plain "2026-03-08" string the language knows how to format. {note.date:.date(long)} shows March 8, 2026.

src/notes.json holds seven notes, each with a Markdown body.

Check it: wf check prints No problems in field-notes. If one note in notes.json has a field that Note does not declare, the check reports T05 at the data line and names the field; if a note leaves out a field Note requires, it reports C01.

Step 3: Write the shell and a layout

The app declaration wraps every page. The current page is drawn where Router stands, inside <main>, so the skip link each page carries jumps past the navigation (Pages and routing). The start of src/App.wf:

wf

// src/App.wf app { use Saved Navbar(class: "site-nav") { Navbar.Brand { Link("Field Notes", to: "/", class: "brand") } Navbar.Links { Link("Notes", to: "/") Link("Tags", to: "/tags") Link(to: "/saved", class: "saved-link") { Text("Saved") if Saved.count > 0 { Badge("{Saved.count}").pill } } Link("About", to: "/about") } Navbar.Actions { ThemeToggle } } Router(transition: .fade, duration: "160ms")
  • The link whose to: is the page shown is marked aria-current="page".
  • ThemeToggle is two icon buttons that call setTheme("dark") and setTheme("light"). The reader's choice is kept across visits.
  • Router(transition: .fade, duration: "160ms") fades one page out and the next in.

Each page names the column it is set in with layout: — a component whose default slot is the page:

wf

// src/components/Sheet.wf /// The column a page is set in, and the frame every page names with /// `layout: Sheet`. A narrow sheet is for reading; a wide one holds a grid. component Sheet(wide: Bool = false) { slot Container(class: ["sheet", if wide { "sheet--wide" }]) { children } }

Check it: the navbar shows Notes, Tags, Saved and About. Click Tags: the page fades over, and the Tags link is marked as the current page.

Step 4: Build a card

A card shows a note at a glance:

wf

// src/components/NoteCard.wf /// A note at a glance: when it was written, its title, a summary, its tags /// and the button that saves it. component NoteCard( _ note: Note, /// Keeps the card in the page but out of sight — what a filter does. hidden: Bool = false ) { Card(class: "note-card", hidden: hidden) { Stack(gap: .sm) { Row(justify: .between, align: .center, gap: .sm) { Text("{note.date:.date(long)} · {note.minutes} min read", class: "note-meta").sm SaveButton(note.slug, title: note.title) } Link(to: "/notes/{note.slug}", class: "note-card__link") { Heading(note.title).h2 } Text(note.summary, class: "note-card__summary") TagList(note.tags) } } }
  • A /// comment above a component or a prop is its documentation. Your editor shows it when you hover a call (Components).
  • A splice may say how to show its value: {note.date:.date(long)} is format(note.date, .date, "long"), written where it is read (Expressions).
  • TagList is a row of #tag links to /?tag=….

Check it: the front page shows a card per note, each with a line such as March 8, 2026 · 4 min read, a title, a summary and its tags.

Step 5: Search and filter the front page

The front page lists every note, narrowed by a search box and by the tag in the address. NoteFinder works the list out:

wf

// src/components/NoteFinder.wf state q = "" derived needle = q.trim().toLowerCase() derived newest = all.sortBy(n => n.date).reverse() derived shown = newest.filter(n => (tag == "" || n.tags.includes(tag)) && (needle == "" || n.title.toLowerCase().includes(needle) || n.summary.toLowerCase().includes(needle))) derived visible = shown.map(n => n.slug) derived allTags = all.flatMap(n => n.tags).unique().sort()

q is bound to the search box, and everything else follows it. sortBy, flatMap and unique are list helpers the language brings. Each also runs at build time, so the pre-rendered page shows the sorted list (State and reactivity).

A static site adds one idea here. Its HTML is written once, before any reader arrives, so the HTML cannot depend on what only the browser knows, such as the address's query or what is in storage. So the finder draws every note and hides the ones that do not match:

wf

// src/components/NoteFinder.wf // Every note is drawn, and the ones that do not match are hidden. // A pre-rendered page cannot know the URL's query, so a list // filtered by it would be missing from the HTML; this way the // page carries every note, and the filter applies once it is live. for note in newest by note.slug { NoteCard(note, hidden: !visible.includes(note.slug)) }

The HTML then holds every note, for a reader without script and for a search engine, and the filter applies the moment the page is live. The front page hands the finder the address's tag:

wf

// src/pages/Home.wf // `query.tag` is the URL's `?tag=…`; it is missing when the URL has // none, and `?? ""` turns that into the finder's "every note". NoteFinder(notes, tag: query.tag ?? "")

Check it: the front page reads 7 of 7 notes. Type tomato in the search box, and the count and the cards narrow as you type. Open /?tag=garden, and only the notes tagged garden show. Run wf build and open build/index.html in a text editor: all seven notes are in it.

If a filtered list is empty in the built HTML, you probably filtered the for itself by query; hide the cards instead, as above.

Step 6: Give each note a page

Each note gets a page at /notes/<slug>:

wf

// src/pages/NotePage.wf page NotePage(path: "/notes/:slug", slug: String, title: "{notes.find(n => n.slug == slug)?.title ?? slug} — Field Notes", description: "{notes.find(n => n.slug == slug)?.summary ?? slug}", type: "article", layout: Sheet, paths: notes.map(n => n.slug)) { derived note = notes.find(n => n.slug == slug)
  • :slug in the path is a typed parameter of the page.
  • paths: names the values a static build renders the page for: one notes/<slug>/index.html per note, each listed in the sitemap (Content).
  • title: and description: may be worked out from the parameters, so each note's search result shows its own title and summary.

The body of the page is the note's Markdown:

wf

// src/pages/NotePage.wf Markdown(n.body)

Markdown renders headings, lists, quotes, emphasis and links, at build time and live. It escapes the text first, so HTML in a note is shown, not run (Elements). Below the note, related lists the three newest notes that share a tag with it — a derived value like any other.

Check it: click a note's title. Its page shows the whole note, and the browser tab shows its title followed by — Field Notes. After wf build, build/notes/ holds seven folders, one per note.

Step 7: List the tags, and write a page in Markdown

The Tags page groups the notes under each tag:

wf

// src/pages/Tags.wf Grid(columns: { base: 1, md: 2 }, gap: .md, align: .start) { for tag in allTags by tag { derived filed = notes.filter(n => n.tags.includes(tag)).sortBy(n => n.date).reverse()
  • A layout prop takes one value per breakpoint: one column on a phone, two from md up. It compiles to a media query, so the first paint is already right (Styling).
  • A derived value inside a for is worked out for each item.

The About page is not a .wf file at all. src/about.md is a page: its front matter names its path, title, description and layout, and the rest is its Markdown:

markdown

--- path: /about title: About — Field Notes description: Who keeps this notebook, why it exists, and how the site is built. layout: Sheet --- # About

Check it: /tags shows one card per tag, in one column on a narrow window and two on a wide one. /about shows the About page in the same column as the others.

Step 8: Keep the reader's saved notes

A store keeps the notes this reader saves:

wf

// src/stores/Saved.wf /// The notes this reader has saved for later, kept in their browser. store Saved { persist slugs: [String] = [] derived count = slugs.length

persist keeps the list in the browser across visits. There is no account, and nothing is sent anywhere (Stores).

The button that saves a note says whether it is pressed, the way assistive technology reads it:

wf

// src/components/SaveButton.wf /// Saves a note for later, or takes it off the saved list. component SaveButton(_ slug: String, title: String) { use Saved Button(if Saved.slugs.includes(slug) { "Saved" } else { "Save" }, aria-pressed: Saved.slugs.includes(slug), aria-label: if Saved.slugs.includes(slug) { "Saved: {title}" } else { "Save: {title}" }, class: "save-button").sm.outlined { on click { Saved.toggle(slug) } } }

Step 2: Describe money

The ledger's types use four of the types the language brings:

wf

// src/types.wf /// Which way the money went. enum Kind { income, expense } /// Something money is spent on, with what the reader means to spend on it /// in a month. type Category { id: String name: String color: Color budget: Money } /// One line of the ledger: money in, or money out. type Entry { id: Uuid date: Date amount: Money kind: Kind category: String note: String = "" }

Money, Date, Color and Uuid are each a plain JSON value at run time (Types). Money is kept in minor units, { amount: 1299, currency: "USD" }, so a sum never drifts by a fraction of a cent. You write it $12.99 and show it with format(m). What the language works out is a call — a.plus(b), a.minus(b), ONE.times(12.5) — and what the value carries is a field: m.amount. Two constants give every sum a starting point:

wf

// src/types.wf /// Nothing yet: the starting point every sum adds to. const ZERO: Money = $0.00 /// One dollar — `ONE.times(12.5)` is $12.50, rounded to the cent. const ONE: Money = $1.00

Check it: wf check prints No problems in pocket. Change $0.00 to $0.001, and the check refuses it: money has two decimals in dollars. Change it back.

Step 3: Add up the ledger

Every figure on every page is a derived value of the Ledger store:

wf

// src/stores/Ledger.wf derived today = now.date() derived newestFirst = entries.sortBy(e => e.date).reverse() derived income = sum(entries.filter(e => e.kind == .income)) derived spent = sum(entries.filter(e => e.kind == .expense)) derived balance = income.minus(spent) derived thisMonth = entries.filter(e => e.date.startOfMonth().isSame(today.startOfMonth())) derived monthIncome = sum(thisMonth.filter(e => e.kind == .income)) derived monthSpent = sum(thisMonth.filter(e => e.kind == .expense)) derived monthBudget = categories.reduce((s, c) => s.plus(c.budget), ZERO) derived budgetLeft = monthBudget.minus(monthSpent)

Add an entry, and the balance, this month's spending, each budget bar and the chart all follow, with no code written to keep them in step (Stores). now is the browser's clock as a value, so today turns over at midnight. sum is an action that only returns a value, which a derived value may call:

wf

// src/stores/Ledger.wf // The money in a list of entries, added up. action sum(list: [Entry]) { return list.reduce((total, e) => total.plus(e.amount), ZERO) }

Check it: the dashboard shows a balance, this month's income and spending, and what is left of the budget. Each is a sum of the sample ledger.

Step 4: Change the stored shape without losing data

What a persist keeps outlives the build that wrote it: a reader who visited last month has last month's shape in their browser. The entries declare which version of the shape this build writes, and how to bring an older one forward:

wf

// src/stores/Ledger.wf // Version 1 of Pocket kept an amount as a plain, signed number of // dollars (`-52.4` was money out). Version 2 keeps a `Money` and a // `Kind`, so `migrate 1 -> 2` turns what a returning reader's browser // holds into the new shape instead of throwing it away. persist entries: [Entry] = SAMPLE_ENTRIES.map(s => Entry( id: s.id, date: now.date().minus(days: s.ago), amount: s.amount, kind: s.kind, category: s.category, note: s.note, )) { version: 2 migrate 1 -> 2 { old.map(e => Entry( id: e.id, date: e.date, amount: ONE.times(Math.abs(e.amount)), kind: if e.amount < 0 { .expense } else { .income }, category: e.category, note: e.note ?? "", )) } }
  • version: 2 says which shape this build writes.
  • migrate 1 -> 2 brings an older value forward. Its body receives the stored value as old.
  • If you raise the version with no migration, the build warns (P01). If you change the shape without raising the version, it warns too (D04), from the shapes it keeps in .wf-cache/ (Stores).
  • A first visit opens on a sample ledger dated from today, so the dashboard is never empty.

Check it: wf check --deny-warnings passes. Delete the migrate block and check again: the check reports P01. Put the block back.

Recipes

These are smaller pieces that most projects need. Each is a whole page you can build and adapt.

Debounce a search

To wait until the reader stops typing before you search, keep what they typed apart from what you search for:

wf

page Search(path: "/", title: "Search", description: "Search as you type, without a request per key.") { state typed = "" state q = "" action commit(value: String) { if value == typed { q = value } } effect { let pending = typed setTimeout(() => commit(pending), 300) } resource hits = fetch("/api/search?q={q}") Heading("Search").h1 Input(bind: typed, placeholder: "Search", aria-label: "Search") match hits { loading { Spinner.sm } error(e) { Text(e.message).danger } ready(list) { Text("{list.length} results for {q}") } } }

The effect runs again on every keystroke, and each run schedules a check. Only the check whose value is still current writes q, and the resource follows q. The timer is the browser's setTimeout, because after(ms) is a declaration with a body, not a statement an effect can hold.

Page through results

To show a long list a page at a time, keep the page number in state and splice it into the address:

wf

page Rows(path: "/", title: "Rows", description: "Every row, twenty at a time.") { state page = 1 state perPage = 20 resource rows = fetch("/api/rows?page={page}&per={perPage}") Heading("Rows").h1 match rows { loading { Spinner } error(e) { Text(e.message).danger } ready(r) { for row in r.items by row.id { Text(row.name) } Row(gap: .sm, align: .center) { Button("Previous", disabled: page == 1) { on click { page = page - 1 } } Text("Page {page} of {r.pages}") Button("Next", disabled: page >= r.pages) { on click { page = page + 1 } } } } } }

A change of page changes the address, so the resource asks again.

Update at once, and roll back on failure

To show a change before the server agrees, keep the old value and put it back if the request fails:

wf

type Item { id: String, liked: Bool } page Likes(path: "/", title: "Likes", description: "A like that shows at once.") { state items: [Item] = [Item(id: "a", liked: false)] state error = "" action like(id: String) { let before = items items = items.map(i => if i.id == id { Item(id: i.id, liked: !i.liked) } else { i }) try { await fetch("/api/like/{id}", { method: "POST" }) } catch e { items = before error = "Could not save. Try again." } } Heading("Likes").h1 for i in items by i.id { Button(if i.liked { "♥" } else { "♡" }, aria-label: "Like").sm { on click { like(i.id) } } } if error != "" { Toast(error).danger } }

optimistic(holder, change) does the same with less code inside an action; see Data.

Build a confirm dialog component

To ask before a destructive action, wrap a Dialog in a component that fires confirm or cancel:

wf

component Confirm(_ title: String, visible: Bool, danger: Bool = false) { event confirm() event cancel() slot Dialog(visible: visible, title: title) { children Row(gap: .sm, justify: .end) { Button("Cancel") { on click { emit cancel() } } Button("Confirm", tone: if danger { .danger } else { .primary }) { on click { emit confirm() } } } } } page Account(path: "/", title: "Account", description: "Close your account.") { state asking = false state gone = false Heading("Account").h1 Button("Delete account").danger { on click { asking = true } } Confirm("Delete your account?", visible: asking, danger: true) { on confirm { gone = true asking = false } on cancel { asking = false } Text("Everything goes. This cannot be undone.") } if gone { Alert("Account deleted.").info } }

The caller's block fills the default slot, so the question's detail is the caller's to write.

Sign in with a session cookie

To sign a reader in without holding a token in the page, describe the service with credentials: .sameOrigin and keep the user in a store:

wf

type User { id: String, name: String } api Auth(base: "/api") { credentials: .sameOrigin get me() -> User post signIn(body: Map) -> User errors { 401 -> Map } post signOut() } store Session { state user: User? = null state checked = false derived signedIn = user != null action load() { try { user = await Auth.me() } catch e { user = null } checked = true } action signIn(email: String, password: String) { user = await Auth.signIn(body: { email: email, password: password }) navigate("/account") } action signOut() { await Auth.signOut() user = null navigate("/") } } page SignIn(path: "/sign-in", title: "Sign in", description: "Sign in to your account.", noindex: true) { state email = "" state password = "" state problem = "" validate email { required email } validate password { required } action send() { problem = "" try { await Session.signIn(email, password) } catch e { problem = "That email and password do not match." } } Heading("Sign in").h1 if problem != "" { Alert(problem).danger } Form(bind: form) { on submit { send() } Input(bind: email, label: "Email").email Input(bind: password, label: "Password").password Button("Sign in", type: .submit, disabled: send.pending).primary } } page Account(path: "/account", title: "Your account", description: "Your account.", guard: Session.signedIn, redirect: "/sign-in") { use Session Heading("Your account").h1 if let u = Session.user { Text("Signed in as {u.name}") } Button("Sign out") { on click { Session.signOut() } } }

The session is an httpOnly cookie the server sets, so the page never holds a token. guard: hides the page from a reader who is signed out, and the server still checks every request (Security). Call Session.load() from the app's set-up, so a returning reader is signed in.

Load more

To add the next page of results below the ones shown, call an endpoint with paginate: .page:

wf

type Item { id: String, name: String } api Catalog(base: "/api") { get items(page: Number = 1) -> [Item] } page Items(path: "/items", title: "Items", description: "Everything, a page at a time.") { state page = 1 resource list = Catalog.items(page: page, paginate: .page) Heading("Items").h1 for item in list.items by item.id { Text(item.name) } if list.hasMore { Button("Load more", disabled: list.state == "loading") { on click { list.loadMore() } } } }

list.items is every item loaded so far, and list.loadMore() asks for the next page.

To let the reader pick light, dark or the system's choice, call setTheme and read theme:

wf

page Settings(path: "/settings", title: "Settings", description: "How the site looks.") { Heading("Settings").h1 Row(gap: .sm) { Button("Light", outlined: theme != "light") { on click { setTheme("light") } } Button("Dark", outlined: theme != "dark") { on click { setTheme("dark") } } Button("Match the system", outlined: theme != "system") { on click { setTheme("system") } } } }

The switch needs a dark theme named in the config (Styling).

Copy to the clipboard

To copy text, call the browser's clipboard from an action:

wf

page Share(path: "/share", title: "Share", description: "Copy the link.") { state copied = false action copy(text: String) { await navigator.clipboard.writeText(text) copied = true } Heading("Share").h1 Button("Copy the link") { on click { copy(location.href) } } if copied { Toast("Copied").success } }

Draw a chart from a library

To use a charting library, list its URL in meta.scripts, call it from a script of your own, and hand it a canvas with Host. The full example is in JavaScript interop.
